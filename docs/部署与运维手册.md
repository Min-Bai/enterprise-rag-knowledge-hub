# 部署与运维手册

## 配置原则

从 `.env.example` 复制生成生产 `.env`，并限制其权限：

```bash
cp .env.example .env
chmod 600 .env
```

`.env` 包含数据库密码、JWT 密钥、模型密钥、邮件授权码和 GHCR 令牌，不得提交到 Git、日志、工单或截图。生产环境应至少设置不同的 `MYSQL_PASSWORD`、`MYSQL_ROOT_PASSWORD` 和足够随机的 `JWT_SECRET_KEY`，并使用：

```env
APP_ENV=production
AUTH_COOKIE_SECURE=true
```

客户端允许来源由 `CORS_ORIGINS` 显式配置。MySQL 不应暴露到公网；需要维护数据库时使用 SSH 隧道。

## 可选能力配置

### 模型用量与成本

管理员在“模型管理”中为每个模型填写输入和输出单价，单位为人民币每百万 Token。系统会记录实际模型调用的 Token、耗时、成功状态和预估成本，并在“模型用量与成本”页面按时间、模型、用户和知识库展示汇总与明细。

只有服务响应中返回 OpenAI-compatible `usage` 字段，且模型同时配置了输入与输出单价时，才会计算预估成本。未返回 Token 用量或未配置单价的调用仍会记录调用次数、结果和耗时，但成本显示为“未配置”。系统不保存问题正文、模型回答或 API Key 到成本记录中。

### 图片 OCR

正式 API 镜像已包含 Tesseract、中文语言包、Pillow 和 pytesseract。启用生产 OCR：

```env
OCR_ENABLED=true
OCR_LANGUAGES=chi_sim+eng
```

图片 OCR 已在生产环境手动验证。修改配置或镜像后需重新创建 `api` 与 `worker` 容器。

### 音频转写

音频转写需要独立的 Whisper 或兼容 OpenAI `POST /v1/audio/transcriptions` 的服务；DeepSeek 不能直接转写音频。配置示例：

```env
TRANSCRIPTION_ENABLED=true
TRANSCRIPTION_BASE_URL=https://transcription.example.com/v1
TRANSCRIPTION_API_KEY=replace-with-real-key
TRANSCRIPTION_MODEL=whisper-1
```

未配置真实服务时，不应将音频转写标记为已通过生产验收。

### QQ 邮箱 SMTP

密码重置邮件可使用 QQ 邮箱 SMTP。`MAIL_PASSWORD` 填 QQ 邮箱授权码，不是网页登录密码：

```env
MAIL_ENABLED=true
MAIL_HOST=smtp.qq.com
MAIL_PORT=465
MAIL_USERNAME=your-account@qq.com
MAIL_PASSWORD=qq-smtp-authorization-code
MAIL_FROM=your-account@qq.com
MAIL_USE_SSL=true
PUBLIC_APP_URL=http://your-host:8080
```

## 开发与本地启动

开发基线为 Python 3.12。启动基础依赖：

```bash
docker compose up -d mysql redis qdrant
```

随后分别启动 API、Celery Worker 与前端开发服务器。开发环境可以构建本地镜像；生产虚拟机不能以本地构建作为发布方式。

## GHCR 自动部署

发布流程如下：

1. 功能分支提交 Pull Request，CI 执行测试和前端构建。
2. PR 合并到 `main` 后，发布工作流构建 API 和 Web 镜像。
3. 镜像以完整 Git SHA 推送至 GHCR。
4. Windows self-hosted Runner 通过 SSH 连接 Ubuntu 虚拟机。
5. 虚拟机拉取指定 SHA 镜像，Compose 更新 `api`、`worker`、`beat` 和 `frontend`，最后验证健康接口。

部署脚本不会执行 `git clean`。若 VM 仓库存在已跟踪源码改动，脚本会先把差异保存为 `~/enterprise-rag-deploy-backups/tracked-changes-时间.patch`，再将源码同步到已验收的发布提交；未跟踪的 `.env`、备份文件和数据卷不会被删除。

Windows 不需要 Docker Desktop。Ubuntu VM 需要 Docker、Compose、SSH，以及对 `enterprise-rag-api` 和 `enterprise-rag-web` 两个 GHCR 包都有读取权限的令牌。

一次性前置条件：

- Runner 标签包含 `self-hosted`、`Windows`、`X64`。
- SSH 主机别名为 `enterprise-rag-vm`，可连接部署 VM。
- 生产目录为 `~/enterprise-rag-knowledge-hub`。
- 生产 `.env`、数据库卷、文档卷、Qdrant 卷和 Redis 卷均已存在。
- VM 已使用 `docker login ghcr.io` 登录并保存有效读取凭据。

镜像必须使用不可变 SHA，而不是仅依赖 `latest`：

```bash
sudo docker pull ghcr.io/min-bai/enterprise-rag-api:sha-<完整提交SHA>
sudo docker pull ghcr.io/min-bai/enterprise-rag-web:sha-<完整提交SHA>
```

部署时必须为 Compose 提供 `API_IMAGE` 与 `WEB_IMAGE`，否则可能回退到 Docker Hub 的旧镜像名并导致拉取失败。

自动工作流已在拉取前检查 `https://ghcr.io/v2/` 的可达性。每个 SHA 镜像最多拉取两次，每次最多八分钟；超时会明确失败，不会无限占用 Runner。不要在工作流拉取期间同时在 VM 手动拉取同一个镜像。

## 生产部署与验证

在 VM 的仓库目录执行：

```bash
sudo docker compose --env-file .env up -d --no-build api worker beat frontend
sleep 10
curl -fsS http://localhost:8000/health
sudo bash scripts/check_production.sh
```

部署完成后确认实际运行的镜像，而不是仅检查工作流成功：

```bash
sudo docker compose ps
sudo docker inspect enterprise-rag-api-1 --format '{{.Config.Image}}'
sudo docker inspect enterprise-rag-frontend-1 --format '{{.Config.Image}}'
curl -fsS http://localhost:8000/health
```

期望健康响应：

```json
{"status":"ok","database":"ok","redis":"ok","qdrant":"ok"}
```

客户端入口是 `/login`，管理端入口是 `/admin/login`。注册和密码重置默认进入管理员审批流程。

## 备份、恢复与回滚

创建 MySQL 备份：

```bash
sudo bash scripts/backup_mysql.sh
```

数据库备份不能替代文档数据卷和 Qdrant 数据卷备份。恢复前必须在临时数据库验证备份，禁止直接覆盖生产数据。

回滚应重新部署一个已发布且验证过的完整 SHA 镜像，不使用 `latest` 判断版本。任何清理前先检查镜像、备份和卷占用；严禁执行：

```bash
docker system prune --volumes
```

该命令可能删除 MySQL、Redis、Qdrant、文档和模型缓存数据卷。

## 日常检查与排障

日常生产检查：

```bash
sudo bash scripts/check_production.sh
```

该脚本检查 Compose 服务、Worker 注册与任务积压、API 依赖、磁盘空间和最近 MySQL 备份。

| 现象 | 处理方式 |
| --- | --- |
| API 健康检查失败 | 执行 `sudo docker compose logs --tail=100 api`，检查 MySQL、Redis、Qdrant 和环境变量。 |
| 前端返回 502 | 先确认 `curl -fsS http://localhost:8000/health` 成功，再执行 `sudo docker compose restart frontend`，让 Nginx 重新解析 `api` 服务。 |
| 文档长期处于等待或处理中 | 查看 `sudo docker compose logs --tail=100 worker`、Worker 注册和 Redis 队列；Worker 恢复后从界面重试。 |
| 文档处理失败 | 查看文档错误原因，修复文件或依赖后重试。 |
| GHCR 拉取卡住或超时 | 工作流会在两次、每次八分钟后失败。先确认旧容器仍在运行，再检查 `curl -I --connect-timeout 10 https://ghcr.io/v2/` 和 `curl -I --connect-timeout 10 https://pkg-containers.githubusercontent.com/`；网络恢复后重新运行部署，不要在工作流运行期间并发手工拉取。 |
| VM 仓库本地改动阻塞部署 | 查看 `git status --short`。新版脚本会自动备份已跟踪改动；旧提交仍阻塞时，先手工备份 `git diff`，再使用旧 Git 兼容命令 `git checkout -- 文件名` 恢复已跟踪文件。未跟踪 `.env` 及备份文件保留。 |
| Compose 尝试访问 Docker Hub | 检查 `API_IMAGE`、`WEB_IMAGE` 是否传入，以及 Compose 中是否意外使用旧镜像名。 |
| API 启动报 Alembic revision 缺失 | 查看 API 日志和当前镜像 SHA；数据库版本与迁移文件不一致时，先备份数据库，再以匹配的发布版本或明确迁移方案处理。 |
| 磁盘空间不足 | 先执行 `df -h` 和 `sudo docker system df`，按保留策略清理无用镜像或过期备份，不删除数据卷。 |

`flower` 是可选运维 Profile，仅绑定 `127.0.0.1:5555`：

```bash
docker compose --profile operations up -d flower
```

不要将 Flower 直接暴露到公网；需要访问时使用私有隧道或受管理员认证保护的反向代理。
